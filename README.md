# AI-powered E2E framework (TesterArmy `e2e`)

This repository holds an end-to-end test setup built on the TesterArmy [`e2e`](https://e2e.tester.army) framework. It includes a small demo login app and one example test, `E2E_LOGIN_001`, that uses AI-driven steps together with deterministic assertions.

```
e2e.config.ts         Framework config: browser target, app URL, AI model, demo credentials
tests/login.e2e.ts    E2E_LOGIN_001: the example login test
tests/example.e2e.ts  Smoke test generated by `npx e2e init` (no AI needed)
demo-app/             Demo app under test (plain Node.js + HTML/CSS/JS, no dependencies)
.env.example          Template for local secrets (copy to .env, which is git-ignored)
.agents/skills/e2e/   Framework docs for coding agents (from `e2e init`)
.mcp.json, .cursor/   MCP server registration for coding agents (from `e2e init`)
```

## Quick start

Requirements: Node.js 24.8+ (or 22.22.3+), plus an OpenRouter API key for the AI steps.

```powershell
npm install

# 1. Add your OpenRouter key (one-time)
copy .env.example .env        # then edit .env (NOT .env.example) and set OPENROUTER_API_KEY
npm run check:ai              # confirms the key is present and accepted, never prints it

# 2. Run the login test (the runner starts the demo app for you)
npm run test:login
```

You can also set the key for the current shell only, instead of writing it to `.env`:

```powershell
$env:OPENROUTER_API_KEY = "sk-or-..."      # PowerShell
export OPENROUTER_API_KEY=sk-or-...         # bash
```

The first run downloads Chromium if it is missing.

## Demo application

| | |
| --- | --- |
| URL | http://localhost:3000 |
| Email | `demo@example.test` |
| Password | `DemoPass123!` |

These credentials are **for the demo only**. They exist only in this local demo and protect nothing.

- A wrong email or password shows the error "Invalid email or password." (`role="alert"`).
- A correct login shows the **Dashboard** heading, a "Welcome, Demo User!" status, and a **Logout** button.
- **Logout** returns you to the login form.

**Do you need a separate terminal?** No. `e2e.config.ts` declares `app.command`, so `npm run test:*` starts `node demo-app/server.js` before the tests and stops it afterwards. The server log goes to `.e2e/logs/app.log`. To try the app in your browser, run it yourself:

```powershell
npm run demo                  # http://localhost:3000, Ctrl+C to stop
```

The config also sets `reuseExisting: true`. If the demo app is already running, the test run attaches to it instead of failing.

## What is the `e2e` framework?

`e2e` is a TypeScript test runner for UI tests. It runs a real browser through Playwright's engine (`@e2e-dev/web`). It also has a built-in **AI agent**: you can describe a step in plain language and let a model carry it out, then check the outcome with exact assertions.

### How it differs from standard Playwright Test

| Playwright Test (`@playwright/test`) | `e2e` |
| --- | --- |
| Every step is code: `page.getByLabel('Email').fill(...)` | Steps can be code (`screen.getByLabel('Email').fill(...)`) **or** goals: `agent.act('sign in')` |
| `page` fixture | `app` (open/restart), `screen` (locators), `browser` (URL, cookies), `agent` (AI) |
| Name matching is a substring by default | `getByRole` names match **exactly** (`'Save'` does not match `'Save changes'`) |
| A locator that matches two elements may still act | Two matches fail immediately with `LOCATOR_AMBIGUOUS` |
| `playwright.config.ts`, `npx playwright test` | `e2e.config.ts`, `npx e2e run` |
| No model involved | Agent steps call an LLM, and passing `act` steps are cached for model-free replays |

Do not reinitialize the project with `npm init playwright`. The `e2e` package already includes the browser engine.

## Anatomy of the example test

`tests/login.e2e.ts` implements **E2E_LOGIN_001: Verify that a user can log in successfully and view the Dashboard.**

| Step | Code | Kind |
| --- | --- | --- |
| 1. Open the login page | `app.open('/')` | Navigation |
| 2. Login page is shown | `expect(screen.getByRole('heading', { name: 'Login' })).toBeVisible()` and the Email/Password fields | Deterministic |
| 3. Enter email and password | `agent.act('Enter {email} ... {password} ...', { params })`, then `expect(Email).toHaveValue(...)` | **AI** + check |
| 4. Submit the form | `agent.act('Click the Login button')` | **AI** |
| 5. Logged-in state | `agent.assert('The user is logged in and the Dashboard is displayed')` | **AI** judgment |
| 6. Dashboard visible | `expect(screen.getByRole('heading', { name: 'Dashboard' })).toBeVisible()` and the welcome status | Deterministic |
| 7. Login form gone | `expect(screen.getByRole('heading', { name: 'Login' })).toBeHidden()` and the Login button | Deterministic |

### `agent.act(goal, options?)`: AI-driven actions

`act` gives the model **one goal**. The model receives a redacted snapshot of the page: roles, accessible names, text, and states. It never receives raw HTML, cookies, or secret values. It then picks tools such as `tap`, `type`, `select`, or `scroll` until it reaches the goal or gives up. The runner validates every tool call, and nothing the model returns is executed as code.

- Put values in `params` and refer to them as `{name}` in the instruction. Do not paste the values into the instruction text.
- The password comes from `credentials.user('demo').password`. It is a `Secret`, so the model sees only its name and the runner types the real value. Screenshots are masked after a secret has been filled.
- Follow each `act` with a check, such as `expect(...)` or `agent.assert(...)`. A passing `act` whose outcome was verified is saved in `.e2e/cache/`, and later runs replay it **without calling the model**.

### `agent.assert(question)`: AI judgment

`assert` asks the model whether a statement is true of the **current** screen. A false statement fails with `ASSERTION_FAILED` and includes the model's explanation. If the screen shows too little to decide, the step fails with `ASSERTION_INCONCLUSIVE`. `assert` is never cached; it always calls the model. It works well for checks that are semantic or fuzzy ("the dashboard looks logged in"), and poorly for exact values.

### `expect()` and accessible locators: deterministic checks

`screen.getByRole('heading', { name: 'Dashboard' })` finds elements the way assistive technology does, by **role** and **accessible name**. It does not use CSS classes or XPath, so it keeps working when the styling changes, and it also confirms that the page is accessible. `expect(...)` retries until the condition holds or the timeout expires (5 s by default), so you never need a `sleep`.

**Why use both?** Model output can vary from run to run, so the test should never depend on AI alone to decide pass or fail. In this test the agent does the interacting and gives a second opinion, while the final verdict comes from exact `expect` checks that always behave the same way.

## OpenRouter and the AI model

The `agent` fixture uses the model configured in `e2e.config.ts`:

```ts
import { openrouter } from '@openrouter/ai-sdk-provider';
agents: { default: { model: openrouter(process.env.OPENROUTER_MODEL ?? 'openai/gpt-6-luna') } }
```

- [OpenRouter](https://openrouter.ai) is a single API that gives you access to many model vendors. The provider package `@openrouter/ai-sdk-provider` reads the **`OPENROUTER_API_KEY`** environment variable. The key never appears in the code.
- **Choosing a model:** set `OPENROUTER_MODEL` to any OpenRouter model ID that supports **tool calling** (see https://openrouter.ai/models). Note that `e2e init` scaffolded `openai/gpt-6-luna-fast`, which OpenRouter does **not** list, so the default here is `openai/gpt-6-luna`.
- **Where to set the key:** put it in `.env` in the project root, in the form `OPENROUTER_API_KEY=your_actual_key_here`. The `e2e` runner does not load `.env` files itself; `e2e.config.ts` loads `.env` with Node's `process.loadEnvFile` before the provider is created. **`.env.example` is only a template: it is never loaded and it is committed to Git, so never put a real key in it.** `.gitignore` excludes `.env` and `.env.*`.
- **Using a shell variable instead:** `$env:OPENROUTER_API_KEY = "..."` only affects the PowerShell window where you run it; a new terminal or the VS Code terminal will not see it. To keep it for every new terminal, run `[Environment]::SetEnvironmentVariable('OPENROUTER_API_KEY', '<key>', 'User')` and then open a new terminal. A shell variable takes precedence over `.env`.
- **Missing key:** the first `agent.*` step fails with
  `MODEL_PROVIDER_FAILED: ... OpenRouter API key is missing ... OPENROUTER_API_KEY` (exit code 3).
  An invalid key fails with `MODEL_PROVIDER_FAILED: ... the provider rejected the credential`.
- **Tests without agent steps** (such as `tests/example.e2e.ts`) need **no model and no key**. Only `agent.act`, `agent.assert`, `agent.waitFor`, and `agent.extract` call the model.
- **Low-credit accounts:** OpenRouter reserves credit for a request's full output limit. The framework's `act` loop sends no limit, which means the model's maximum of 65,536 tokens, and its judgments send 8,192. Both can fail with `This request requires more credits, or fewer max_tokens` even though the actual cost is a fraction of a cent. `e2e.config.ts` caps every request at 4,096 tokens through the provider's `extraBody`. Change the cap with `OPENROUTER_MAX_TOKENS`, or add credits at https://openrouter.ai/settings/credits.
- **Cost:** each `act` uses up to 25 model calls and each `assert` uses up to 2. `npm run test:e2e:debug` prints the tokens and cost of each step.

## Inspecting failures

After every run:

| Where | What |
| --- | --- |
| Terminal | The failing step, error code, message, and a code frame |
| `.e2e/report.json` | Every test, attempt, step, error, and artifact path |
| `.e2e/artifacts/web/<test>/default/attempt-N/failure/screen.txt` | What the page contained when the step failed |
| `.../attempt-N/screenshots/001-failure.png` | A screenshot taken at the failure |
| `.../attempt-N/trace/trace.zip` | A Playwright trace for each attempt (traces are on by default locally) |
| `.e2e/summary.md`, `.e2e/failures/` | Readable failure pages (`--reporter list,markdown` or `npm run test:e2e:debug`) |
| `.e2e/ai-trace.json` | Every model call: what the agent saw and did (`--ai-trace`, included in `test:e2e:debug`) |
| `.e2e/logs/app.log` | Demo app server output |

The framework has no HTML report server. Start with the terminal output, `.e2e/failures/*.md`, or `report.json`. Other useful tools:

- `--headed` watches the browser while the test runs.
- `npx playwright show-trace <trace.zip>`, or https://trace.playwright.dev, opens a trace file listed in `report.json`.

Common error codes:

| Code | Usual cause |
| --- | --- |
| `LOCATOR_NOT_FOUND` | The role or name is wrong (names match exactly) |
| `LOCATOR_AMBIGUOUS` | The locator matches more than one element |
| `ASSERTION_FAILED` | The model judged the statement false; read its explanation |
| `MODEL_PROVIDER_FAILED` | The key is missing or wrong, there are no credits, or the model ID is unknown |
| `APP_UNREACHABLE` | The app did not start or answer; check `.e2e/logs/app.log` |

See `npx e2e guide debugging` for the full list.

## Using a real application later

1. Make the app reachable: start it yourself and set `APP_URL`, for example `APP_URL=http://localhost:4200` for `ng serve`. When `APP_URL` is set, the config does not start the demo app. To have the runner start your app, change `app.command` in `e2e.config.ts`, for example `{ executable: 'npx', args: ['ng', 'serve', '--port', '4200'] }`.
2. Supply real test-account credentials through `E2E_USER_DEMO_USERNAME` and `E2E_USER_DEMO_PASSWORD`, or rename the `credentials` entry. Keep them in `.env` or CI secrets, never in code.
3. Update the locators to match your app's accessible names. Learn the names from the markup, by running `--headed`, or by having your coding agent drive the app over MCP (see below).
4. Add one test file per feature under `tests/` (`*.e2e.ts`).
5. The demo app is self-contained in `demo-app/`, so you can delete it when you no longer need it.

## Runtime AI agent vs. MCP for coding assistants

These are two separate uses of AI:

| | Runtime agent (`agent` fixture) | MCP server (`.mcp.json`) |
| --- | --- | --- |
| Who uses it | The **test** while it runs | **Your coding assistant** (Claude Code, Cursor) while you write tests |
| Configured in | `agents` in `e2e.config.ts` (OpenRouter) | `.mcp.json` / `.cursor/mcp.json` → `npx e2e mcp` |
| Model and key | Your `OPENROUTER_API_KEY` | The coding assistant's own model; the MCP server itself needs no key |
| Purpose | Perform `act` goals and `assert` judgments in CI and locally | Let the assistant open the live app, observe it, and check locators before writing a test |

The `.agents/skills/e2e/` folder (linked from `.claude/skills/e2e`) teaches coding assistants the framework's API. Both pieces come from `e2e init` and are left unchanged here.
